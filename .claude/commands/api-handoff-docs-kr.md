# 백엔드 → 프론트엔드 인수인계 문서화

백엔드 작업이 완료된 후 프론트엔드 개발자를 위한 포괄적인 API 인수인계 문서를 생성하는 Claude Code 스킬입니다.

## 목적

이 스킬은 구조화된 API 인수인계 문서 작성을 자동화합니다. 프론트엔드 개발자(또는 그들의 AI 어시스턴트)가 백엔드 개발자와 반복적으로 질문을 주고받지 않고도 API 연결과 UI를 구축하는 데 필요한 완전한 비즈니스 및 기술 컨텍스트를 제공합니다.

## 사용 시점

다음과 같은 경우에 이 스킬을 사용하세요:

- 백엔드 API 작업이 완료되었을 때 (엔드포인트, DTO, validation, 비즈니스 로직 구현 완료)
- 프론트엔드 연결을 위해 API 변경 사항을 문서화해야 할 때
- 기능이 백엔드와 프론트엔드 팀 간 인수인계 문서를 필요로 할 때
- 프론트엔드가 API 연결을 올바르게 구축할 수 있도록 모든 컨텍스트를 확보하고 싶을 때
- 사용자가 명시적으로 요청할 때: "인수인계 만들기", "API 문서화", "프론트엔드 인수인계", "API 문서"

**시점**: 백엔드 구현을 완료한 후, 프론트엔드 개발이 시작되기 전에 실행하세요.

## 작동 방식

1. 완료된 백엔드 코드(release branch 기준, 현재 branch의 변경사항)를 **분석** (엔드포인트, 컨트롤러, 서비스, DTO, 검증)
2. 비즈니스 컨텍스트, 제약 조건, 엣지 케이스, 주의 사항을 **추출**
3. 모든 통합 세부 정보가 담긴 구조화된 마크다운 문서를 **생성**
4. `.claude/docs/ai/<feature-name>/api-handoff.md`에 **저장**
5. 이후 업데이트를 **버전 관리** (v2, v3 등)하여 반복 작업 추적

### 워크플로우

```bash
백엔드 코드 → 스킬 분석 → 인수인계 문서 → 프론트엔드 구현
```

스킬은 "no-chat" 모드로 동작합니다. 논의나 설명 없이 인수인계 문서만 생성합니다.

## 주요 기능

### Comprehensive Coverage

- **비즈니스 컨텍스트**: 문제 정의, 사용자, 도메인 용어
- **엔드포인트 세부 정보**: 메서드, 경로, 인증 요구사항, swagger URL, API summary
- **데이터 모델**: TypeScript 인터페이스, 필드 타입, null 허용 여부, enum
- **검증 규칙**: 프론트엔드 UX를 위한 필수 필드, 제약 조건, 형식
- **비즈니스 로직**: 명확하지 않은 동작, 엣지 케이스, 주의 사항
- **테스트 시나리오**: 정상 흐름(happy path), 오류 케이스, 인수 기준

### Smart Shortcuts

명확한 검증과 복잡한 비즈니스 로직이 없는 단순 CRUD API의 경우, 스킬은 전체 템플릿을 건너뛰고 다음만 제공할 수 있습니다:

- 엔드포인트 + 메서드, swagger URL
- 엔드포인트에 대한 요약 설명

나머지는 프론트엔드가 추론할 수 있습니다.

### 버전 관리

피드백이나 변경 후 문서를 다시 생성할 때 반복 접미사(`-v2`, `-v3`)를 자동으로 증가시킵니다.

## 사용 예시

### 예시 1: 전체 기능 인수인계

```
사용자: "경비 승인 API를 막 완성했어. 프론트엔드를 위한 인수인계 문서를 만들어줘."

- POST /api/expenses/:id/approve 엔드포인트 세부 정보
- swagger URL
- status enum (pending, approved, rejected)
- 검증 규칙 (금액 한도, 필수 필드)
- 엣지 케이스 (한 번만 승인 가능, 관리자 전용 권한)
- 정상/오류 흐름에 대한 테스트 시나리오

## 모범 사례

### 백엔드 개발자용

1. **완료 후 실행**: 백엔드 작업이 끝났을 때만 인수인계 문서 생성
2. **컨텍스트 포함**: 프론트엔드가 도메인 로직을 안다고 가정하지 말 것
3. **실제 예시**: 플레이스홀더가 아닌 실제 요청/응답 페이로드 사용
4. **주의 사항 노출**: 구현 중 발견한 엣지 케이스를 문서화
5. **버전 업데이트**: 피드백 후 API가 변경되면 다시 생성

### 프론트엔드 개발자용

1. **문서 신뢰**: 필요한 모든 컨텍스트는 인수인계 문서에 있어야 함
2. **누락 표시**: 불명확한 부분이 있으면 구체적인 내용과 함께 v2 요청
3. **테스트 시나리오 활용**: 프론트엔드 테스트 케이스나 인수 기준으로 변환
4. **타입 검증**: 제공된 TypeScript 인터페이스를 사용해 타입 안전성 확보

## 포함되지 않는 것

스킬은 의도적으로 다음을 제외합니다:
- 백엔드 구현 세부 정보 (파일 경로, 클래스 이름, 내부 서비스)
- 데이터베이스 스키마 또는 내부 데이터 구조
- 배포 또는 인프라 세부 정보
- 백엔드 테스트 전략

오직 통합 계약(integration contract)과 비즈니스 컨텍스트에만 집중합니다.

## 출력 예시

스킬이 생성하는 내용의 샘플은 다음과 같습니다:

```markdown
# API Handoff: Expense Approval

## Business Context
직원이 경비를 제출하면 관리자가 승인합니다. 관리자는 선택적 코멘트와 함께
검토하고 승인/반려합니다. 승인된 경비는 환급을 위해 회계로 넘어갑니다.
도메인 용어: "Submitter"(직원), "Approver"(관리자), "Reimbursable"(승인됨).

## Endpoints

### POST /api/expenses/:id/approve
- **목적**: 경비 제출 건을 승인 또는 반려
- **인증**: 관리자(Manager) 역할 필요
- **swagger URL**: https://api-commerce.dev.keeperplatform.com/api-docs#/common/CommonController_pong_v1
- **응답** (오류): 관리자가 아니면 403, 경비를 찾을 수 없으면 404, 이미 승인됐으면 422
- **참고**: 한 번만 승인 가능. 작업은 영구적임 (실행 취소 불가).

## Data Models / DTOs

```typescript
interface ExpenseApprovalDto {
  decision: 'approved' | 'rejected';
  comment?: string; // 최대 500자
}

interface ExpenseDto {
  id: number;
  status: 'pending' | 'approved' | 'rejected';
  approvedBy?: string;
  approvedAt?: string; // ISO 8601
}
```

## Validation Rules
- `decision`: 필수, 'approved' 또는 'rejected'여야 함
- `comment`: 선택, 최대 500자, 공백 제거(trim) 처리됨
- 프론트엔드는 코멘트 필드에 글자 수 카운터를 표시해야 함

## Business Logic & Edge Cases
- 승인하려면 관리자(Manager) 역할이 있어야 함
- 본인 경비는 승인할 수 없음 (백엔드에서 강제)
- 승인/반려되면 결정은 최종임 (재승인 불가)
- soft delete된 경비는 404 반환

## Integration Notes
- **권장 흐름**: 경비 조회 → 승인 모달 표시 → 결정 제출 → 목록 새로고침
- **낙관적 UI**: 권장하지 않음 (권한 검사가 실패할 수 있음)
- **실시간**: 웹소켓 이벤트 없음. 승인 후 폴링 또는 수동 새로고침

## Test Scenarios
1. **정상 흐름**: 관리자가 대기 중 경비 승인 → 업데이트된 상태와 함께 200
2. **검증 오류**: 빈 decision → 검증 메시지와 함께 422
3. **권한 거부**: 관리자가 아닌 사용자가 승인 시도 → 403
4. **이미 승인됨**: 같은 경비를 두 번 승인 → 422 충돌(conflict)
```

## 관련 스킬

- **frontend-to-backend-requirements**: 백엔드 개발자를 위해 프론트엔드의 데이터 요구사항을 문서화 (역방향)
- **code-reviewer**: 생성된 인수인계 문서의 완전성을 검토할 수 있음
- **dev-spec**: API 설계를 포함할 수 있는 전체 개발 명세를 생성

## 팁

1. **최신 상태 유지**: API 계약이 변경되면 다시 생성
2. **PR에서 링크**: 백엔드 PR 설명에서 인수인계 문서를 참조
3. **버전 관리**: 팀 가시성을 위해 인수인계 문서를 git에 커밋
4. **프론트엔드 피드백 루프**: 프론트엔드가 질문한다는 것은 인수인계 문서가 무언가를 놓쳤다는 의미이므로 업데이트할 것
5. **명세로 활용**: 구현 전에 API 명세로서 인수인계 문서를 생성할 수도 있음
